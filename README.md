# Glum

Glum is a notes and todos app with authenticated sharing and optional Google Calendar sync. The backend is a Rust gRPC service with a small HTTP auth surface for Google OAuth, data lives in PostgreSQL, and the local browser client is a Svelte app that talks to the backend through Envoy's gRPC-Web proxy.

## Repository Contents

```text
glum/
├── backend/              Rust backend, protobufs, SQL migrations, Dockerfile, Kubernetes manifests
│   ├── src/              gRPC services, Google OAuth auth routes, calendar sync, auth interceptor
│   ├── protobufs/        Notes, todos, and users API definitions
│   ├── migrations/       SQLx migrations for notes, todos, users, sharing, and calendar sync
│   └── k8s/              Local Kubernetes manifests for kind
├── web/                  Svelte/Vite web UI used for local testing
│   └── src/gen/          Generated protobuf DTOs and Connect clients for the web app
├── deploy/               Shared deployment config, including the Envoy config used by Compose
├── docker-compose.yml    Lean Docker Compose stack for NAS/local deployment
├── CONTEXT.md            Project notes/context
└── mise.toml             Local task runner commands
```

## Technology

- Backend: Rust, Tokio, tonic, axum, SQLx, PostgreSQL.
- API: protobuf/gRPC. Rust server types are generated by `tonic-build`; web DTOs and clients are generated by Buf into `web/src/gen`.
- Auth: direct Google OAuth. The backend exchanges the Google auth code, stores/updates the Google user in PostgreSQL, and issues a Glum JWT for gRPC requests.
- Calendar: Google Calendar API using each user's stored Google refresh token.
- Web test client: Svelte 4, Vite, Connect-Web/gRPC-Web.
- Mobile client: Expo React Native in `frontend/`.
- Local infra: Docker Compose or kind/Kubernetes, Envoy gRPC-Web proxy, PostgreSQL.

## Google OAuth Setup

Create or reuse a Google OAuth web client in Google Cloud. Enable the **Google Calendar API** for the same Google Cloud project.

For local development, add these authorized redirect URIs to the OAuth client:

```text
http://localhost:4000/auth/google/callback
```

The OAuth consent screen must request/test the Calendar scope:

```text
https://www.googleapis.com/auth/calendar.events
```

If the app is still in Google Testing mode, add every test Gmail account under the OAuth consent screen's test users.

For Docker Compose, put the OAuth credentials in `.env`.

For local Kubernetes, create the secret with your OAuth credentials:

```bash
kubectl create secret generic google-oauth-secret \
  -n glum \
  --from-literal=client-id='YOUR_GOOGLE_CLIENT_ID' \
  --from-literal=client-secret='YOUR_GOOGLE_CLIENT_SECRET'
```

For non-local deployments, also change:

- `GOOGLE_REDIRECT_URI`
- `WEB_URL`
- `APP_JWT_SECRET`

in [backend/k8s/backend.yaml](/home/berran/Projects/glum/backend/k8s/backend.yaml).

## Docker Compose Setup

Docker Compose is the simplest way to run Glum on a NAS. It runs:

- `postgres`
- `backend`
- `envoy`
- `web`

Only the web container needs to be exposed to your LAN. The web container proxies `/auth/*` and gRPC-Web requests to Envoy internally.

Create your environment file:

```bash
cp .env.example .env
```

Edit `.env`:

```text
WEB_PORT=4000
HTTPS_PORT=8443
GLUM_HOST=glum-app.duckdns.org
GLUM_PUBLIC_URL=https://glum-app.duckdns.org:8443
POSTGRES_PASSWORD=change-this-password
APP_JWT_SECRET=change-this-to-a-long-random-string
GOOGLE_CLIENT_ID=your-google-client-id.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=your-google-client-secret
```

For Google OAuth, add this authorized redirect URI:

```text
https://glum-app.duckdns.org:8443/auth/google/callback
```

Start it:

```bash
docker compose up -d --build
```

For local Compose builds from source, use the build override:

```bash
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

The default `docker-compose.yml` uses prebuilt images from GitHub Container Registry so Portainer can deploy it without building images on the NAS.

Open:

```text
https://glum-app.duckdns.org:8443
```

The backend runs SQL migrations automatically on startup.

Stop it:

```bash
docker compose down
```

Keep the database volume:

```bash
docker compose down
```

Delete the database volume too:

```bash
docker compose down -v
```

## Kubernetes Setup

Start the local Kubernetes cluster:

```bash
mise run cluster:up
```

Wait for Postgres to be ready:

```bash
kubectl rollout status deployment/postgres -n glum --timeout=180s
```

Forward Postgres and run migrations:

```bash
kubectl port-forward -n glum svc/postgres 5432:5432
mise run migrate
```

Build and load the app images into kind:

```bash
mise run load-image
mise run load-web
```

Forward the local services used by the web app. Run these in separate terminals and leave them running:

```bash
kubectl port-forward -n glum svc/web 4000:80
kubectl port-forward -n glum svc/postgres 5432:5432
```

You can also use the helper task:

```bash
mise run test:forward
```

Open the web UI at `http://localhost:4000`.

## Auth and Sharing Model

The web app redirects to `/auth/google/login` through Envoy. The backend exchanges the Google OAuth code, stores the user in the app database, and redirects back to the web app with a Glum JWT. Every gRPC-Web request sends `Authorization: Bearer <token>`.

The backend verifies Glum JWTs with `APP_JWT_SECRET` and scopes notes/todos to the Google `sub` claim. Notes and todos have an owner, and owners can share an item with another Glum user. Shares can be read-only or editable through the `can_write` flag.

The `Users` gRPC service lists users from the app database for the share picker.

## Google Calendar Sync

Todos can be synced to the current user's primary Google Calendar. Calendar sync is per user, not per todo globally, so a shared todo can create a different Google Calendar event for each Glum user.

The backend refreshes Google Calendar access with the current user's stored Google refresh token and calls the Google Calendar API directly. A todo needs a due date before it can be synced. Glum creates an all-day transparent calendar event, updates it when the current user edits/toggles the synced todo, and removes it when that user turns sync off.

Current limitation: when one user edits a shared synced todo, Glum updates that user's calendar event during that request. Other shared users can refresh their own calendar event by pressing the todo's calendar sync button again.

## Database

PostgreSQL tables are managed by SQLx migrations in `backend/migrations/`:

- `users`
- `notes`
- `todos`
- `note_shares`
- `todo_shares`
- `todo_calendar_syncs`

Run migrations with:

```bash
mise run migrate
```

## Notes

- The database password and `APP_JWT_SECRET` in local manifests are development defaults only.
- Google refresh tokens are currently stored in the app database. For production, use a strong database backup/encryption story and a real `APP_JWT_SECRET`.
- The Expo app in `frontend/` is present, but the Svelte app in `web/` is the current local test UI.
